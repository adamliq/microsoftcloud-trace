The new platform is measured against the company's logging baseline: which categories are required per resource type, which destinations are approved, and how long data must be kept. What actually reaches those destinations is read from the diagnostic settings on each resource (including the ones Azure Policy deploys), the VM agents and other sources. Edit a setting or the baseline to see how deficiencies change. The page writes nothing to Azure: it collects your edits as pending changes and generates the commands to apply them. A live version would read the settings through the Azure Monitor diagnostic settings API.

How to get these files from Azure

Resources: JSON with id, name, type (and optional layer), or a CSV with those columns. Use type Subscription for the activity log and Tenant for Entra ID.

az graph query -q "Resources | where resourceGroup =~ 'rg-contoso-shop-prod' | project id, name, type, kind"   --first 1000 --query data -o json > resources.json

Diagnostic settings: the output of az monitor diagnostic-settings list for each resource, combined into one JSON array. You can pick several files at once.

jq -r '.[].id' resources.json | while read -r id; do
  az monitor diagnostic-settings list --resource "$id" --query "value || @" -o json
done | jq -s 'add' > diagnostic-settings.json

# Activity log and Entra ID (optional, separate files)
az monitor diagnostic-settings subscription list --query "value || @" -o json > activity-log-settings.json
az rest --method get --url "https://management.azure.com/providers/microsoft.aadiam/diagnosticSettings?api-version=2017-04-01-preview"   --query value -o json > entra-settings.json

The resources JSON export also carries each VM's OS log collection (data collection rule, SIEM agent and audit policy) under osCollection, and importing it restores them. The CSV export holds resources only.

The JSON export also carries a model for each resource: everything the page knows beyond the catalog, such as categories that don't apply, coverage that happens outside diagnostic settings (SQL auditing, workspace-based Application Insights, Defender alerts, flow logs) and metric categories. Importing it rebuilds the resource exactly. Files without a model get rules by type instead, using kind when present (for example, function app logs only apply to function apps).

Imported settings become the baseline, so pending changes show only what you edit afterwards. The exports use the same formats, so they can be imported again.

Coverage matrix

Each cell counts the categories of that kind the baseline requires for the resource, and how many meet it: collected, in an approved destination, and kept long enough. Green means all of them, amber some or partly, red none, and a dash means the baseline requires none of that kind. “gap” marks important categories of resource types the baseline has no rules for. Tap a cell to open the resource and its settings.

Can we answer these questions?

Each investigation needs specific log sources. A question is answerable only when every source it needs is covered. Tap a source to open its resource.

How the baseline works: a category is required when its catalog severity is at or above the level set in the baseline panel, unless you override it for that resource type. A required category meets the baseline when it is collected into an approved destination: a Log Analytics workspace, the SIEM, or an archive the baseline approves. The page records how each one gets there (diagnostic setting, Azure Policy, Azure Monitor Agent, SIEM agent, continuous export and so on). Anything short of that is a deficiency; a recommended category that falls short is an advisory. Categories that don't apply to a resource are listed but never required. Resource names, IDs and the sample baseline are fictional. Edits, imports and the baseline are kept in this browser only.
