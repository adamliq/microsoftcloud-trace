Inventory both the user-facing sign-in and every API/workload identity. One application can use SAML for its users, a managed identity for a service call, and LDAP for authorisation. Record each relationship separately.

Authentication factors, provisioning and authorisation

Passwords, passkeys/FIDO2, Windows Hello for Business, Microsoft Authenticator and user certificate-based authentication are ways to authenticate the user. They sit beneath the application’s SAML/OIDC flow. A client certificate used by a daemon is a workload credential, not user CBA.

SCIM and Entra provisioning create/update users and groups; collect ProvisioningLogs and target lifecycle records. They do not establish a user session. App roles, delegated scopes, application permissions and resource RBAC govern access; token issuance alone does not prove the application allowed an operation.

Collect the relevant Entra log categories through tenant diagnostic settings → Azure Event Hub → a configured Splunk input, or an explicitly supported API collector. A Universal Forwarder on an application server collects its local logs; it does not collect tenant Entra logs by reading Windows event channels.

Discovery and validation for existing Entra apps

  1. Enumerate enterprise applications/service principals and app registrations; capture tenant ID, client ID, object ID, owners, SSO configuration, credentials, consent and permission grants.
  2. Use representative interactive, non-interactive, service-principal and managed-identity sign-ins to identify active clients and resources. Registration alone does not prove use; no recent sign-ins alone does not prove retirement.
  3. Inspect code/configuration and perform a controlled test to establish grant, credential, identity, target resource and application authorisation behaviour.
  4. Correlate with local process/service telemetry, resource logs and the lab’s AD discovery methods to identify LDAP, Kerberos, NTLM and service-account dependencies.
  5. Classify each relationship as existing Entra, Entra + AD bridge, or AD-backed; record owner, evidence, last seen, exceptions and next action in the inventory.

Notes

  • 4768 / 4771 handle AS-REQ (TGT) traffic. Certain pre-auth failures (especially 0x18) appear as 4771.
  • 4769 / 4770 handle TGS-REQ (service ticket) traffic.
  • 4624 is the session-creation event on the *target* machine. When AuthenticationPackageName = Kerberos, it is the result of earlier ticket issuance.
  • Correlate equal, nonzero LogonGuid values between 4769 (DC) and 4624 (target host) when populated; corroborate account, time, client and service. Cached tickets and collection gaps can prevent a complete chain.

Event 4768 – TGT Requested (Key Fields)

Account Information

  • TargetUserName – Account requesting the TGT (computer accounts end with $)
  • TargetDomainName – Supplied Realm Name
  • TargetSid – SID of the account (often NULL SID on failures)

Service Information

  • ServiceName – Usually krbtgt (or krbtgt/REALM on failures)
  • ServiceSid – SID of the krbtgt account

Network Information

  • IpAddress – Client IP (IPv4, IPv6, or ::ffff:x.x.x.x)
  • IpPort – Client source port (0 for localhost)

Additional Information

  • TicketOptions – Hex flags (common: 0x40810010)
  • Status – Result code (0x0 = success)
  • TicketEncryptionType – Encryption used for the ticket
  • PreAuthType – Pre-authentication type (2 = normal password, 0 = no pre-auth)

Newer fields (Windows Server 2016+ with recent cumulative updates):

ResponseTicket, AccountSupportedEncryptionTypes / AccountAvailableKeys, ServiceSupportedEncryptionTypes / ServiceAvailableKeys, DCSupportedEncryptionTypes / DCAvailableKeys, ClientAdvertizedEncryptionTypes, SessionKeyEncryptionType, PreAuthEncryptionType.

Event 4769 – Service Ticket Requested (Key Fields)

  • TargetUserName (often UPN format)
  • TargetDomainName
  • ServiceName / ServiceSid
  • TicketOptions, TicketEncryptionType, Status
  • IpAddress, IpPort
  • LogonGuid (correlates with 4624)
  • Newer: RequestTicketHash, ResponseTicketHash, encryption-type fields

Event 4771 – Pre-Authentication Failed (Key Fields)

  • TargetUserName, TargetSid
  • ServiceName (usually krbtgt/REALM)
  • TicketOptions, Status (Failure Code), PreAuthType

Event 4624 – Successful Logon (Key Fields)

  • LogonProcessName
  • AuthenticationPackageName → Kerberos, NTLM, or Negotiate
  • LmPackageName (NTLM only: NTLM V1 / NTLM V2)

2. Authentication Methods Used with Active Directory

Kerberos

  • Preferred protocol since Windows 2000.
  • Ticket-based (TGT → TGS). Passwords are not sent after the initial exchange.
  • Requires correct DNS resolution, time synchronisation within configured Kerberos policy (commonly five minutes), and properly registered SPNs.
  • Supports AES (preferred) and legacy RC4.
  • Negotiate may fall back to NTLM when Kerberos cannot be used and both the application and security policy allow it. A Kerberos failure does not guarantee fallback.

Common consumers: Domain logons, SMB/CIFS shares, SQL Server integrated authentication, IIS Windows Authentication, RDP, print services, many internal LOB applications, constrained/unconstrained/resource-based constrained delegation.

Entra impact: Not natively supported for arbitrary on-prem services. Options include Entra Application Proxy + Kerberos Constrained Delegation, Microsoft Entra Domain Services, Cloud Kerberos Trust (limited scenarios), or a residual AD footprint.

NTLM (v1 and v2)

  • Challenge-response protocol (legacy).
  • NTLMv2 is significantly stronger than NTLMv1 but remains vulnerable to relay and pass-the-hash attacks.
  • Used when Kerberos fails or by older applications and appliances that only support NTLM.

Detection:

  • 4624 with AuthenticationPackageName = NTLM
  • 4776 on Domain Controllers
  • Microsoft-Windows-NTLM/Operational log (especially Event 8004)

Entra impact: No native equivalent. Treat ongoing NTLM usage as technical debt that must be discovered and reduced.

LDAP / LDAPS

  • Simple bind – username (DN or UPN) + password (clear-text unless protected by LDAPS or StartTLS).
  • SASL – usually GSSAPI (Kerberos) or GSS-SPNEGO (Negotiate → Kerberos or NTLM).
  • Ports: 389 (LDAP), 636 (LDAPS), 3268/3269 (Global Catalog).

Common consumers: Linux/Unix systems (SSSD, Winbind), custom applications and scripts, appliances, printers, scanners, HR systems, monitoring tools, older identity/provisioning systems.

Entra impact: No native LDAP endpoint. Options: Entra Domain Services, modernise to Microsoft Graph / OAuth, supported provisioning where appropriate (provisioning does not replace the LDAP authentication endpoint), or residual AD.

Negotiate (SPNEGO)

  • Windows security package that negotiates the best mutually supported protocol.
  • Almost always tries Kerberos first and falls back to NTLM.
  • Appears in 4624 as AuthenticationPackageName = Negotiate. Treat as “Kerberos preferred, NTLM possible”.

Certificate-based / Smart Card / PKINIT

  • User presents a certificate (smart card or software certificate).
  • Entra ID supports Certificate-Based Authentication (CBA), but AD smart-card / PKINIT and Entra CBA are different authentication paths. Validate certificate trust, mappings, client support, revocation and authentication-strength policy.

3. Discovering Authentication Usage and Applications

A. Event Log / SIEM Analysis (Highest Value)

Kerberos

  • Collect 4768, 4769, 4771 from all Domain Controllers.
  • Key fields: ServiceName, TicketEncryptionType (0x17 = RC4), Client Address, PreAuthType, Status.

NTLM

  • 4624 where AuthenticationPackageName = NTLM
  • 4776 on Domain Controllers
  • Enable and collect Microsoft-Windows-NTLM/Operational (Event 8004 is especially useful – shows client, server, and user).

LDAP

  • Use endpoint/network discovery plus application configuration. Directory Service Access auditing is not a complete LDAP bind inventory.
  • LDAP interface event logging
  • Network/firewall logs for ports 389/636/3268/3269

Correlate source IP or computer name to application owners.

B. NTLM Restriction Auditing (Built-in)

Use the Group Policy settings under:

Computer Configuration → Windows Settings → Security Settings → Local Policies → Security Options

  • Network security: Restrict NTLM: Audit Incoming NTLM Traffic
  • Network security: Restrict NTLM: Audit NTLM authentication in this domain
  • Network security: Restrict NTLM: Outgoing NTLM traffic to remote servers

Start in Audit mode. Do not enforce until the inventory is complete and remediation plans exist.

C. Application & Service Inventory

  • Service accounts with SPNs:

setspn -F -Q */* or LDAP filter (servicePrincipalName=*)

  • IIS sites with Windows Authentication enabled
  • SQL Server instances using Windows Authentication
  • File servers, print servers, NAS devices
  • Linux/Unix systems using SSSD, Winbind, or LDAP binds
  • Custom line-of-business applications, scheduled tasks, and scripts
  • Appliances (scanners, printers, storage, monitoring, backup tools)

D. Network / Firewall Data

Look for traffic to Domain Controller ports:

  • 88 – Kerberos
  • 389 / 636 – LDAP / LDAPS
  • 445 – SMB (often NTLM or Kerberos)
  • 3268 / 3269 – Global Catalog

5. Considerations for Moving to Entra-Native

Identity & Authentication Model

  • Prefer Password Hash Sync (PHS) as the primary method for most organisations (resilient, enables leaked-credential detection).
  • Plan for passwordless as the target state (Windows Hello for Business, FIDO2/passkeys, Microsoft Authenticator passwordless).
  • Decide Source of Authority for users and groups (which objects will become cloud-managed).

Applications

  • Modern apps are the easiest wins.
  • Kerberos/NTLM web apps usually need Application Proxy + KCD or Private Access as a bridge.
  • LDAP apps are often the hardest and longest-lived reason for residual AD.
  • Service accounts and non-human identities frequently become the critical path.

Devices

  • Move from Hybrid Azure AD Join toward pure Entra Join + Intune where feasible.
  • Group Policy must be replaced by Intune Configuration Profiles / Settings Catalog.
  • Use Group Policy Analytics in Intune to identify migratable settings.

Residual Active Directory Patterns

Common end-states:

  • Fully Entra-native (rare in complex enterprises in the short term)
  • Minimised AD kept only for remaining Kerberos/LDAP consumers
  • Microsoft Entra Domain Services (managed domain in Azure that still speaks Kerberos, NTLM, and LDAP)
  • Long-term hybrid with clear sunset dates for residual workloads

Security & Operations

  • Deploy Conditional Access, Identity Protection, and phishing-resistant MFA before large-scale cutover.
  • Test with pilot users and applications; keep dual paths during transition.
  • Monitor authentication failure rates closely after every change.
  • Treat privileged accounts and break-glass accounts with extreme care.

8. Service Accounts & Non-Human Identities

These are frequently the longest-lived AD dependencies.

Inventory actions

  • Identify all accounts with SPNs
  • Identify accounts used by Windows services, scheduled tasks, IIS app pools, SQL services, middleware, and appliances
  • Note password age, whether the account is a gMSA, and whether the password is known/shared

Target patterns

  • Group Managed Service Accounts (gMSA) where still on AD
  • Managed Identities (Azure) for cloud workloads
  • Workload Identity / federated credentials where possible
  • Eliminate shared/privileged service accounts with static passwords
9. Recommended Phased Approach
  • Inventory & Discovery (current focus)

Authentication methods, SPNs, NTLM usage, LDAP consumers, application matrix.

  • Enable & Harden Hybrid Identity

Prefer Password Hash Sync, deploy Conditional Access baseline, enable Identity Protection, configure break-glass accounts.

  • Move Modern / Federated Applications

AD FS relying parties and SaaS apps → Entra enterprise applications.

  • Device Management Transition

Hybrid Join → Entra Join + Intune; begin Group Policy replacement.

  • Tackle Kerberos / NTLM / LDAP Applications

Application Proxy + KCD, modernisation, Entra Domain Services, or residual AD isolation.

  • Reduce AD Footprint

Decommission unnecessary DCs and trusts; move remaining workloads if feasible.

  • Shift Source of Authority

Move users and groups to cloud management where applications allow.

10. Risks, Pitfalls & Validation

Common pitfalls

  • Under-estimating NTLM and LDAP usage
  • Forgetting service accounts and appliances
  • Breaking Kerberos by accessing resources via IP
  • Missing SPNs or duplicate SPNs
  • Clock skew
  • Cutting over applications without pilot validation
  • Removing AD FS or DCs before all relying parties are migrated
  • Assuming Entra Domain Services is a full AD replacement (it is a subset)

Detection Quick Wins

  • Repeated 4771 / 0x18 across many accounts from one source warrants password-spray investigation; exclude stale stored credentials and other benign failures.
  • Repeated unknown-account failures (0x6, commonly 4768) warrant enumeration investigation; validate source, stage and baseline.
  • Successful 4768 with PreAuthType 0 plus confirmed disabled pre-authentication can identify AS-REP roasting candidates; failure records alone are insufficient.
  • Unusual RC4 (0x17) service-ticket requests across services/accounts warrant investigation; RC4 alone does not prove Kerberoasting.
  • A missing 4768 is a visibility lead, not proof of a forged ticket: check ticket cache/lifetime, other DCs, time range, trusts and collection coverage.

Clarifications applied to this edition

  • LDAP lookup, synchronisation and user authentication require separate classifications. Use the lab’s LDAP discovery workflow; diagnostics are not a complete bind audit.
  • Cloud provisioning, Microsoft Graph and managed identities require application and resource support. They do not replace an arbitrary LDAP password bind, gMSA or machine-account logon.
  • PKINIT and Entra CBA are separate flows. Negotiate does not prove Kerberos was selected. Nonzero matching Logon GUIDs provide corroboration when available.
  • RC4, pre-authentication failures and missing TGT records are investigation leads requiring context; they do not establish an attack on their own.
  • Cloud Kerberos trust, Azure Files Entra Kerberos and Entra Domain Services have different scopes. Verify each workload rather than treating them as general AD replacements.
  • Separate source-of-authority, lifecycle synchronisation, device enrollment, authentication, provisioning and authorisation decisions in the migration plan.
