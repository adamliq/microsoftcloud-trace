    LDAP · discovery and verification
    Find LDAP clients. Confirm what each application does.
    Use network discovery to find LDAP clients, trace their connections to applications, then confirm how they authenticate. AD does not maintain a complete register of applications using LDAP.
    LDAP traffic is not proof of LDAP user authentication.
    An application might query groups, synchronise accounts, or check authorisation after a SAML, OIDC or Kerberos login. Keep the bind account separate from the application’s end user.
    1 · Find clients2 · Map applications3 · Enrich evidence4 · Confirm behaviour5 · Record findings
    

    1. Find systems connecting to domain controllers
    Search firewall, network-flow or endpoint telemetry for connections to all DCs, including Global Catalog servers. Include IPv4 and IPv6 and account for NAT, proxies or LDAP load balancers when mapping the original client.
    Destination TCP portServiceInterpretation
    389LDAP; can also use StartTLSPort alone does not identify bind method or transport protection.
    636LDAPSEncrypted transport does not tell you whether the app authenticates users.
    3268Global Catalog LDAPDirectory lookup may be unrelated to user login.
    3269Global Catalog LDAPSProtected Global Catalog traffic remains a discovery candidate.
    Collect source host/IP, destination DC, destination port, first/last seen and connection count. Observe a representative business cycle to include scheduled and infrequently used apps. Distinguish telemetry record counts from actual connections: one connection may produce multiple flow records. Absence from a limited observation window does not prove absence of LDAP usage.
    

    2. Map each connection to its application
    Use EDR network telemetry or Sysmon Event ID 3 on Windows application servers to identify the executable, ProcessId and ProcessGuid. Sysmon network logging is disabled by default and requires configuration. Match process evidence to the connection’s time; PIDs can be reused.
    PowerShell · live connection snapshot
    Get-NetTCPConnection -State Established |
    Where-Object { $_.RemotePort -in 389,636,3268,3269 } |
    Select-Object LocalAddress, RemoteAddress, RemotePort, OwningProcess,
        @{Name='Process';Expression={
            (Get-Process -Id $_.OwningProcess -ErrorAction SilentlyContinue).ProcessName
        }}
    This is a snapshot and can miss short-lived connections. For shared processes such as java.exe or w3wp.exe, map the PID to its service, application pool, container or deployment. A process name alone may represent multiple applications.
    

    3. Add DC-side evidence—and understand its limits
    2889 discovers qualifying insecure binds; it is not a complete LDAP authentication audit. On each monitored DC, record the previous diagnostic value, enable level 2 for the collection window, then restore the recorded value.
    PowerShell · enable and restore LDAP interface diagnostics
    # Run locally on each DC being monitored, with appropriate privileges.
$path = 'HKLM:\SYSTEM\CurrentControlSet\Services\NTDS\Diagnostics'
$name = '16 LDAP Interface Events'
# Record the existing value in the change record before enabling diagnostics.
Get-ItemProperty -Path $path -Name $name
Set-ItemProperty -Path $path -Name $name -Value 2

# After the collection window, restore the recorded prior value.
# Replace <recorded value> with that number; do not assume it was 0.
# Set-ItemProperty -Path $path -Name $name -Value <recorded value>
    Review Event Viewer → Directory Service → Event ID 2889 for client IP and attempted bind identity. Signed LDAP and protected LDAPS usage will not be comprehensively discovered by this event.

    4. Confirm whether LDAP actually authenticates users
    Inspect the application’s identity configuration and correlate a controlled test login: time, app request, source host/process, directory connection, bind identity and final login/access result. With TLS, network telemetry alone cannot reveal the bind sequence; use authorised application logs/configuration rather than infer it from the port.
    Observed application behaviourClassification
    Searches for a user, then binds using that user’s credentialsLDAP user authentication
    Binds as a service account only to retrieve users / groupsDirectory lookup; user authentication still needs confirmation
    Uses SAML / OIDC / Kerberos for login, then LDAP for group checksLDAP authorisation lookup
    Periodically imports AD users / groupsDirectory synchronisation
    These are common patterns, not an exhaustive list of LDAP authentication mechanisms. Record bind mechanism (simple or SASL), protection (TLS / signing) and purpose separately. Keep service accounts, gMSAs, computer accounts and user identities distinct. One application can have multiple LDAP purposes; use separate register rows where useful.
